# 评估上线、回滚与安全（Gate + Registry + Watchdog + Safety + Audit）

> 模块：`src/engine/gates.py`、`registry.py`、`watchdog.py`、`safety.py`；
> 接口契约见 `docs/03` §4.5–4.8。本文回答：**凭什么让一个候选上线、上线后怎么监控、
> 坏了怎么回滚、整个过程怎么保证可审计与不受控**。

## 1. 上线门禁 Gate：多证据、保守拒绝

### 1.1 判定项与公式

`Gate.evaluate(candidate, incumbent, ctx) -> GateResult`，逐项写入 `criteria`
（`{name: {value, threshold, pass, note}}`），全部通过才 `decision="promote"`。

| 判据 | 公式/口径 | 阈值（配置） | 设计依据 |
|---|---|---|---|
| `probe_gain` | $\Delta = F1^{cand}_{eval} - F1^{base}_{eval}$；baseline 优先用**候选自带的同批留出 champion 指标** `baseline_probe_macro_f1`，否则退回 incumbent | `gates.min_gain_points = 0.01` | 探针 4–6 条标签的准确率噪声约 ±0.17，不能作为唯一基线；同批留出标签的 baseline 与候选配对比较，噪声小一个量级（见 §1.2） |
| `recall_drop` | $\max(0,\ R^{base}_{min}-R^{cand}_{min})$，$R_{min}$=类别召回最小值 | `max_recall_drop = 0.12` | 防"总体 F1 涨但某类完全塌陷"（工业场景漏检一类故障不可接受） |
| `recall_floor` | 候选类召回绝对下限 | `min_class_recall_floor = 0.0`（可按需提高） | 硬底线 |
| `calibration` | $\Delta ECE = ECE^{cand}-ECE^{base}$ | `calibration_slack = 0.04` | 概率输出用于下游决策/告警，校准不能显著恶化 |
| `cost` | `cost.scalar`（compute + 0.02·labels + 1e-5·tokens） | `max_cost_per_update = 40.0` | 单位更新成本上限 |
| `reproducibility` | 候选模型 state 往返后预测一致（tol 1e-6）；或 registry 保存 npz 后重新加载校验 | `repro_tol=1e-6` | 不可复现的模型不可审计、不可回滚 |
| `budget` | 剩余标签/算力非负（loop/工具已先过滤，此处兜底） | — | 预算硬约束 |
| `human_gate` | 高风险 playbook（NOVEL_CLASS_EXTEND/RETRAIN_MIXED）需人工批准；校赛封闭评测 `safety.auto_approve_high_risk=True` 时以 **escalation 记录**代替人工（写入 criteria 与 safety.escalations） | `high_risk_gain_multiplier=1.5`（增益门槛 ×1.5） | 高风险动作必须有额外安全边际；封闭评测无人值守但**留痕可查** |
| `shadow` | `gates.shadow_required=True` 时要求先影子评估 N 窗口 | `shadow_windows=2` | 可选灰度 |

**保守原则**：候选指标缺失/NaN 时判**拒绝**，绝不抛异常（封闭评测里异常=事故）。
软性告警（校准/成本）只记录不阻塞，但会写进 `reason`。

### 1.2 为什么门禁要用"同批留出标签"的 baseline

集成期实测：monitor 探针只有 4–6 条标签时，准确率是 1/n 的离散台阶（±0.17~0.25），
用 `candidate_f1 − probe_acc(6 labels)` 做 0.01 阈值判定会被噪声淹没：
- 一个真实 +0.05 的改进可能被 6 标签噪声判为 −0.10 → **该上线没上线**；
- 一个 0 改进可能因探针恰好偏低而"通过" → **不该上线上线**。

修复（已实现）：playbook 在自己的留出评估集（16–32 条）上同时算候选与 champion
指标，写进 `metrics.baseline_probe_macro_f1 / baseline_class_recall_min / baseline_ece`；
Gate 优先采用它（`base_src = candidate.baseline_probe_macro_f1(同留出集)`），
同时仍把 incumbent 的探针值也记进 criteria 供审计对照。这条改动让 S7 闭环从
"门禁在噪声上反复横跳"变成"一次 TTA 部署即 +8.8pt 且后续无错误上线"。

### 1.3 决策语义

- `passed=True` → `decision="promote"`（loop 随后 `registry.add()+promote()`）；
- 否则 `decision="reject"`，`reason` 列出失败项（如 `拒绝: probe_gain,recall_drop`）；
- 高风险且 `safety.auto_approve_high_risk=False` 且无人工批准 → `human_gate` 失败 → reject；
- 影子动作（SHADOW_ONLY）由 playbook 返回 `model=None` 实现"不替换 champion"，
  不进入 promote 分支（避免门禁通过后误上线影子候选）。

## 2. 模型仓库 Registry：不可变版本与完整 lineage

### 2.1 不变量

1. **版本不可变**：版本号单调递增；artifact 路径（`<run>/registry/vNNNN.npz`）已存在时
   拒绝覆盖（`RuntimeError`），新版本只能新文件；
2. **可复现**：`add()` 保存后立即 `MLP.load()` 重新加载，校验预测一致（失败抛错，
   不产生脏版本）；`MLP.state()` 已包含 scaler、hidden 结构、TTA 标记
   （`_adaptive`），因此 **TTA 能力随版本入库、回滚后仍保留**；
3. **lineage 完整**：每版记录 `parent`、`playbook`、`config`、`metrics`、`cost`、
   `n_classes`；`lineage_of(version)` 可回溯完整链；
4. **类别数可变**：基座 4 类，NOVEL_CLASS_EXTEND 可产生 5 类版本，仓库按模型实际
   `n_classes` 存档（构造参数只作元数据参考）；回滚到 4 类版本后闭环继续工作。

### 2.2 指针与事件

状态 `registry.json` 原子写（tmp + `os.replace`），包含：
`versions[]`、`champion`（版本号指针）、`next_version`、`events[]`。

- `promote(v)`：当前 champion → `archived`，v → `champion`，记 `{kind:"promote",
  version, previous}`；
- `rollback(to, reason)`：当前 champion → `rolled_back`，to → `champion`，
  记 `{kind:"rollback", to_version, from_version, reason}`；
- 每次 promote/rollback 由 loop 额外写 `RunRecord` 与审计哈希链（决策可追溯）。

### 2.3 回滚 SOP

```
触发条件（任一）：
  a) watchdog.observe() 连续 rollback_window 窗口平滑下降 > max(rollback_drop_points, 0.12)；
  b) 诊断=repair 且存在可回滚历史版本（registry.champion().version>0）；
  c) 人工/kill-switch。
执行：registry.rollback(to_version, reason) → monitor.on_promote(new_champion)（参考域重建）
     → watchdog.reset() → audit.append({type:"rollback", to_version, reason})
降级：若无 previous version（champion 是基座 v0）或工具层拒绝 → 记录原因并 NOOP，
     不做半失效的回滚（fail-closed）。
```

## 3. 上线看门狗 Watchdog

### 3.1 规则

`observe(t, phase, score, champion_version) -> {action, reason, drop}`，score 越大越好
（loop 传探针准确率；无探针时传 `mean_margin` 代理）：

1. champion 版本变化 → 重建参考（返回 `none`，避免拿旧模型基线冤枉新模型）；
2. `ref` 由健康窗口的 EMA 维护；`smooth = α·score + (1−α)·smooth`（α=0.5）；
3. `drop = ref − smooth`；**`drop > max(rollback_drop_points, min_drop_abs)` 连续
   `rollback_window=3` 个窗口 → `action="rollback"`**；
4. 回升到参考附近 → `action="recover"`（用于记录"自愈/恢复"事件并复位计数）。

### 3.2 为什么 `min_drop_abs=0.12`

契约里 `rollback_drop_points=0.03`。但集成期实测发现：monitor 探针只有 4–6 条标签时，
准确率的量化误差是 1/n = 0.17–0.25，`0.03` 阈值会被**正常波动**击穿（例如真实准确率
0.95 时，一次 5/6 探针就让"drop=0.12"），导致误回滚（集成期实测出现过 2 次误触发）。
因此看门狗采用 `max(0.03, 0.12)`：既保留配置语义（真实劣化 >> 0.12），又吸收小样本
探针的量化噪声。S7 上真实漂移窗口的探针准确率下降通常 0.2–0.6，远大于 0.12，
所以真回滚能力不受影响。**这是一处文档化的工程取舍**，配置可覆盖。

### 3.3 实测

- 稳定流：`[0.95]*4` 后若分数在 0.86–0.96 间波动（4–6 条探针的正常噪声）→ 不触发；
- 持续劣化：连续 4 个窗口 0.30–0.40 → 第 3 个 bad 窗口触发 rollback；
- champion 更替（TTA 上线）后首个窗口重建参考，不会因"新模型 vs 旧基线"误回滚。
- 单测覆盖：`tests/test_engine.py::TestWatchdog`（含噪声容忍用例）。

## 4. 安全护栏 SafetyGuard

`check(action, payload, state) -> (allowed, checks)`，逐项检查并写入 `Decision.safety`：

| 检查 | 规则 | 配置 |
|---|---|---|
| kill-switch | `STOP` 文件存在（`kill_switch_files`，支持多路径）时只允许 NOOP/ROLLBACK 等收尾动作 | `kill_switch_file(s)` |
| 动作白名单 | playbook 必须在 `safety.allowed_playbooks` | 9 个 playbook |
| 预算硬门 | 标签/算力/token 不得超剩余；单决策标签 ≤160；playbook 名义标签需求也要 ≤剩余 | `max_labels_per_decision` |
| 单窗口更新次数 | `max_updates_per_window=1`；每 phase 次数受 `BudgetState.per_phase_updates` 约束 | `budget.per_phase_updates=3` |
| 连续失败上限 | 连续失败 ≥3 → 只允许回滚/NOOP | `max_consecutive_failures=3` |
| 决策/token 上限 | `max_decisions=80`；单决策 token ≤20000 | — |
| 网络禁止 | 运行期任何网络动作被拒绝（`allow_network=False`） | 安全要求 |
| 高风险升级 | 高风险 playbook 需人工批准或 escalation 自动记录（写入 `guard.escalations`，可审计） | `auto_approve_high_risk`、`human_gate` |

**受控 RSI 边界**：LLM/Harness 只能从白名单动作 + 预算内实验中选择；策略层只能改
"先验分"，不能改护栏/门禁/预算；kill-switch 与连续失败上限保证系统不会陷入
"无限自我修改"。

## 5. 审计日志 AuditLog：sha256 哈希链

### 5.1 结构

每行一条 JSON 记录：

```json
{"seq": 7, "prev_hash": "<sha256 of previous line>", "hash": "<sha256>",
 "record": {"type": "decision", "t": 18, "chosen_playbook": "RECALIBRATE_AFFINE", ...}}
```

哈希公式（docs/03 §4.7 契约）：

$$
hash_i = \mathrm{sha256}\big(prev\_hash_{i-1} \,\Vert\, canonical\_json(record_i)\big),
\qquad prev\_hash_0 = \text{"0"}\times 64
$$

`canonical_json` = `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",",":"))`。
append 后 `fsync`；`verify()` 逐行重算并检查 `seq` 单调、`prev_hash` 链接、`hash` 值，
任一篡改都会被发现（`tests/test_engine.py` 与 `test_engine_integration.py` 均有篡改用例）。
`last_hash()` 写入 run 结果（`result["audit"]["last_hash"]`），供外部复核。

### 5.2 审计覆盖面

一次 run 的审计日志包含：`decision`（诊断+候选+预算前后+成本+护栏）、`experiment`、
`deploy`、`rollback`、`safety_block`、`playbook_error`、`tracker_error`、
`monitor_rebase_error` 等事件。全部决策可由
`Decision → RunRecord/SwanLab run → 代码+配置+seed` 追溯；
`result.json` 中 `audit.verified=True` 是验收硬指标之一（当前全矩阵均为 True）。

### 5.3 已知集成注意

`src/cli.py` 早期另写了一套 `verify_audit`（把 seq/prev_hash 一起入哈希），与契约公式
不一致，会把本实现的审计日志判为 BAD；已向 Lead 提出改用
`from src.engine.safety import AuditLog; AuditLog(path).verify()`，避免两套实现漂移。
（`AuditLog.verify()` 是契约唯一权威实现。）

## 6. 双门不变量与失效方向（配套研究 J3 映射；criteriond 不变量对照）

配套研究 J3（criteriond，未投稿）证明判据是"有状态、可复制"的对象：同一带内攻击下滚动中位数
尺度→接受一切、EMA→拒绝一切，宽门在 4/4 轨迹爆炸而双门隔离以 90.68% 隔离率恢复严格门质量；
其部署不变量（无部分版本、每版本一个赢家、隔离多数派 fail-closed、确认写不丢）与我们的
registry/审计链/kill-switch 语义一一对应。实现见 `src/engine/monitor.py`（详见 docs/04 §4）：

1. **双门不变量**：参考域（判据状态）只在"门禁通过 + 有锚定标签"后更新
   （`monitor.on_promote()` 是唯一更新入口）；被拒绝/证据不足的窗口只写
   `provisional_ref`（审计字段 `provisional_ref_update`），不改变报警基线。
2. **失效方向指示器**：每窗口记录 `accept_rate / reject_rate / n_trigger_recent /
   n_accept_recent / n_suppressed_recent / failure_direction ∈ {accept_all,
   reject_all, balanced} / n_accepted_total`；watchdog 记录 `rollback_count /
   last_action`。审计可据此判断系统是否退化为"接受一切"或"拒绝一切"，并触发
   固定阈值对照策略（人工介入/上报）。

### 6.1 criteriond 不变量对照（J3，单进程版）

配套研究 J3（criteriond，未投稿）给出 5 条多副本部署不变量。我们是**单进程 + 本地文件/哈希链**实现，
不声称多副本容错；把不变量映射成 6 条可执行断言（脚本 `scripts/check_invariants.py`，在 main/scenarios/real
共 **27 个 run** 上检查）：

| J3 不变量 | 我们的断言 | 检查方法 | 结果 |
|---|---|---|---|
| I5 连续版本序列 | C1 版本连续且唯一 | registry 版本 0..N 连续、无重复 | 27/27 ✅ |
| I2 无部分版本 | C2 artifact 可加载 | 每个版本 npz 存在且可 `MLP.load` | 27/27 ✅ |
| I5 每版本恰一个赢家 | C3 每版本至多晋升一次、最终 champion ≤1 | deploy 记录去重 + registry 状态 | 27/27 ✅ |
| I1/I4 写入前置条件 | C4 deploy 必有门禁通过记录 | 决策 outcome.gate.passed + champion 指向 | 27/27 ✅ |
| I4 fail-closed | C5 rollback 目标存在且曾在位 | 审计/版本表比对 | 27/27 ✅ |
| I1 确认写不丢/可追溯 | C6 审计哈希链可校验 | `AuditLog.verify()`（无事件视为空链通过） | 27/27 ✅ |

结论：**27/27 run 全部通过**。这组断言把 J3 的"判据必须有状态、可恢复、写入前置、每版本一个赢家"
落成了可检查的工程语义；多副本/quorum/分区容错不在本项目范围。

### 6.2 带内扰动负向测试（J3 式，独立脚本）

脚本 `scripts/negative_inband_test.py`（不改变 161 项单元测试计数；结果
`results/tables/negative_inband_test.*`）：

- **A. 门禁边界负向测试**（8 个用例，`Gate` 真实代码）：
  带内 +0.4pt / +0.99pt 均拒绝；恰好 +1.0pt / +1.1pt 放行；候选指标 NaN 拒绝；
  候选与 incumbent 都缺基线时拒绝（fail-closed）；类召回塌陷 -0.2 拒绝；
  "基线缺失但 incumbent 可用"按设计回退 incumbent 基线并记录来源。→ **8/8 符合预期**。
- **B. 重复带内扰动**：10 次带内候选（增益 0.4–0.95pt）→ **放行 0/10**，无累积放行。
- **C. 双门不变量源码级断言**：`active_ref` 的写入函数集合 ⊆ {`reset_reference`, `on_promote`}；
  `_maybe_rebase` 只写 `provisional_ref`（隔离区）→ **3/3 通过**。

结论：带内扰动下我们的门禁**fail-closed**，不会因"边界附近的微小增益"悄悄上线，也不会把被拒样本
写进已接受参考域；J3 中"中位数→接受一切 / EMA→拒绝一切"的两终态风险，由**固定阈值 + 双门隔离**
挡在门外（对照数字见 §6）。

## 8. 风险、限制与后续

1. **探针噪声与门禁/看门狗**：4–6 条标签只能支撑"粗粒度"性能判断；当前靠"同批留出
   标签 + 阈值下限 + 连续窗口"三重稳健化。若预算允许，把探针提到 10–12 条是最直接的改进。
2. **高风险自动升级**：校赛封闭评测用 `auto_approve_high_risk=True` + escalation 记录
   代替人工；正式部署应改为审批流（配置切换即可，接口已留）。
3. **回滚的"无 previous version"降级**：repair 场景若 champion 仍是基座 v0 或工具层
   拒绝回滚，当前策略是记录原因并 NOOP（fail-closed），不执行半失效回滚；
   集成期实测 t=35/39 的 repair 触发会走到这条降级路径。
4. **策略表跨 run 隔离**：已改为 per-run 策略表（`planner.policy_path` 由 loop 按
   run_dir 注入），避免 A7 复现性被跨 run 状态污染；如需跨 run 学习，应显式指定
   全局策略表并做版本快照（criteriond 的轻量版）。
